# dsh-ai-rename

A [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) plugin that suggests a
conversation title generated by the current model, shown underneath the session rename input.

Open a session's rename dialog and a suggestion row appears below the field — **click it to copy
the suggestion into the input**. Nothing is applied automatically.

## Why click-to-apply instead of auto-renaming

DSH's session-title service **pins** a session the moment a title is set explicitly: after that,
automatic revisions stop. Writing a generated title automatically would therefore fight the
built-in title system for ownership.

The suggestion is a *candidate value*, not a title. The row never calls `sessionTitle.rename()`,
so DSH keeps sole ownership of the real title, and a rename stays a deliberate user action.

## What it does

- Reuses the same generation path the built-in title provider streams through (`ctx.llm` with
  `purpose: 'session-title'`), so adapter-specific behavior such as disabling thinking applies.
- Summarizes the **most recent** task, not the first prompt — a different trade-off from the
  shipped `first-prompt` provider.
- Reads the model route the session actually recorded, so the suggestion follows the conversation's
  own model rather than a configured default.
- Only considers genuine human messages (`user/message` with `source.kind === 'user'`); injected
  plugin messages are excluded.

## Settings

A "Title suggestion" section is contributed to the Settings panel.

| Setting | Meaning |
| --- | --- |
| Model / Free text / Summary | Which parts compose the suggestion, toggled independently (a Logic-style asset-export pattern). A live preview shows the composed result. |
| Auto refresh | Regenerate each time the rename dialog opens. |
| Keep when pinned | For a session you renamed yourself, reuse the last suggestion instead of regenerating. |
| Recent messages | How many recent human messages feed the summary. |

## Install

The plugin has two halves, and **both matter**:

- `lib/index.js` — host half. Owns one exact HTTP route, generates the summary.
- `lib/client.js` — browser half. Injects the row and registers the settings section.

### 1. Build

```sh
node build.mjs
```

No bundler is used. The host half is plain ESM that Node imports directly; the browser half only
needs wrapping in the loader factory shape, which `build.mjs` does.

### 2. Link into a profile

```sh
dsh plugin --profile web add /path/to/dsh-ai-rename
```

### 3. Remove it from `dsh.profile.bundles`

This step is **required**, and the reason is not obvious.

DSH Desktop market-checks every entry in `dsh.profile.bundles` against the npm registry. A locally
linked package has no published version, so the lookup returns 404 and Desktop reports
*"plugin failed to start"* and ejects it from the profile.

Keep the package in `dependencies` (so pnpm links it into `node_modules` and the loader can resolve
its name), keep it **out** of `bundles`, and insert its loader row from the profile's patch layer
instead:

```yaml
# profiles/<name>/cordis.patch.yml
- insert:
    - id: title-suggest
      name: dsh-plugin-title-suggest
```

The plugin's own `package.json` therefore deliberately declares **no** `dsh.bundle` — that field is
what marks a package as a bundle layer and triggers the market check.

### 4. Restart

The plugin tree is composed once at harness startup. `patchReload: live` only re-applies patches to
rows that are already composed, so it cannot introduce a new plugin row. `restart-dsh.sh` quits the
app, relaunches it, and polls until the plugin's route answers.

> The package name is still `dsh-plugin-title-suggest` while the repository is `dsh-ai-rename`.
> Renaming the package would mean re-linking every profile that references it.

## How the row finds the dialog

The rename dialog renders its body as a hard-coded `[input, error?]` array and declares **no slot**
anywhere inside it, so a `MutationObserver` is the only way to reach that position without patching
the shipped bundle.

Locating it is done by shape, never by class name or label text:

- CSS-module class hashes (`WL7F9W_renameInput`) change on every build;
- `aria-label` and the dialog title are localized strings.

The session and workspace rename dialogs are **structurally identical** — both portal a
`div[role="dialog"][aria-modal="true"]` whose body is a single autofocus text input, with no
description and no per-dialog `className`. Verified against `dsh-client-ui-workspace`, so no
structural test separates them.

The rule therefore **excludes** known workspace titles and accepts everything else matching the
rename shape, rather than requiring one exact session title. That keeps the row working under a
locale this revision has never seen, and the failure direction is deliberate: the worst case is a
suggestion row under a same-shaped dialog, never a crash and never a write into a field the user
did not ask about.

## How the row finds the session

Opening a session row's **Rename** menu does *not* open that session, so the store's current
selection is not the rename target — it is just whatever session happens to be open. Reading
`current` alone would silently suggest a title for the wrong conversation.

So the row reads the target out of the dialog's own React state: the workspace browser keeps it as
`{ sessionId, currentTitle }` in a `useState`, reachable by walking up the fiber chain from the
dialog input. Requiring **both** keys is what makes the probe specific — the workspace rename
dialog, which is otherwise indistinguishable, stores `{ workspaceId, currentTitle }`.

If the fiber shape ever moves, the row falls back to `ctx.sessions.list.getSnapshot().current` —
the same projection `useSessions` and `dsh-client-ui-conversation` read — and finally to
`no session selected`. Note that `getListSnapshot()` is a `SessionManager` method and **not** part
of the `sessions` service surface; calling it on the service returns `undefined` through optional
chaining, which is exactly how a working plugin ends up reporting `no session selected` forever.

## Security

The route is owned as an exact path outside the `/api` prefix, so `dsh-client-connection` does not
authenticate it. That is the cost of avoiding the Typert code-generation step, which an out-of-tree
plugin cannot participate in. The server binds loopback only, and the handler narrows it further:
it rejects non-local peers, foreign `Host` headers (DNS rebinding), and cross-site browser requests.

```sh
curl -H "sec-fetch-site: cross-site" http://127.0.0.1:53612/plugin/title-suggest
# -> 403 {"ok":false,"error":"loopback requests only"}
```

## Layout

```
src/index.js        host half  (route, generation, loopback guard)
src/client.js       client half (DOM injection, settings section)
build.mjs           produces lib/index.js and lib/client.js
cordis.patch.yml    loader row for the plugin
restart-dsh.sh      restart + verify helper
lib/                build output (not edited by hand)
```

## Known limitations

- **DOM injection is coupled to dialog shape.** If DSH restructures the rename dialog, the row
  stops appearing. It degrades to "no row" rather than misbehaving.
- **The rename target is read through React internals** (`__reactFiber$…` → hook chain). If that
  state is renamed or moved, the probe returns nothing and the row falls back to the current
  session, which can be a different one; the row's label is the only hint.
- **Settings live in `localStorage`**, not host state, so they are per-browser rather than
  per-profile.
- **The host half has no harness runtime dependencies** and deliberately reconstructs the small
  user-message shape instead of importing `@deepseek-ai/dsh-llm`. A plugin linked outside the
  profile's `node_modules` cannot resolve harness packages — Node walks up from the plugin's own
  directory and never reaches the app's — and a runtime import there fails the whole profile boot.
